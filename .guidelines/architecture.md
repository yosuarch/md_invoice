# Technical Architecture

## Tech Stack
- **Backend:** CodeIgniter 4.7 (PHP 8.6)
- **Frontend:** Bootstrap 5.3 + Bootstrap Icons (served locally from `public/assets/vendor/`)
- **Database:** MariaDB (InnoDB, utf8mb4_unicode_ci)
- **Auth:** CodeIgniter Shield
- **AI Integration:** Local Model (Gemma 4) via Ollama/Continue; Claude Code

## Database
The full schema, conventions and business rules are in **`database.md`** — it is the source of truth.
- Migrations in `app/Database/Migrations/`, built on `App\Database\Support\BaseMigration` (shared column helpers).
- Lookup data in `app/Database/Seeds/LookupSeeder.php` (idempotent; run `php spark db:seed DatabaseSeeder`).

## Authentication & Authorization
- **Shield only.** No custom users/roles tables; never hash passwords manually.
- Roles are Shield groups in `app/Config/AuthGroups.php`: `admin`, `sales`, `finance`, **(rev)** `warehouse`. Public registration is disabled; an admin creates staff accounts.
- Extra user columns (`full_name`) via `App\Models\UserModel` (Shield user provider).
- Protect routes with filters: `session` for any staff user, `permission:invoices.manage` etc. for actions (several permissions = any of them: `permission:customers.view,proposals.manage`). In code: `auth()->user()->can('invoices.void')`.
- **Record-level access:** `App\Services\AccessScope` (`records.view_all` = admin, finance). Lists use `$this->scope()->proposals($query)` / `invoices()` / `customers()`; detail actions start with `$this->guardProposal($id)` / `guardInvoice()` / `guardDelivery()` / `guardCustomer()` (404 when hidden). Every new list, detail page, PDF, API or upload must apply the scope. `ensureRep()` creates a sales rep for a sales user who has none (quick-add school).

## Backend Structure
- CodeIgniter 4 MVC. **Models** for all database access; **Controllers** stay thin and call models/services; **Views** only render.
- Money is handled as strings/DECIMAL; round with `round(..., 2)` per line before summing.

### Screen language (i18n) **(rev)**
- Every screen text comes from CodeIgniter language files: `app/Language/{id,en}/<Module>.php`, read with `lang('Module.key', [args])`; both locales have identical keys (checked by `ProductVariantsTest`). Shared words in `App.php`, menu in `Nav.php`, stored codes (statuses, types, kinds, groups, document types) in `Labels.php` via `code_label('group', $code)`, service/controller messages in `Messages.php`, model field labels and custom validation messages in `Fields.php` (`<table>__<field>`, `msg__<table>__<field>__<rule>`, applied automatically by `BaseModel`), Indonesian core validation messages in `id/Validation.php`, JS texts in `Js.php` (exposed as `window.AppLang`, read with `App.t('key', ...args)`), lookup screens via `localize_lookup()` (`Lookups.php`, English falls back to `Config\Lookups`).
- Default locale `id` (`Config\App`), supported `id` / `en`. `App\Filters\LocaleFilter` (global) applies `users.locale` (or the guest's session choice); `POST locale` (`Locale::switch`) saves it; toggle `components/language_toggle` in the top bar and on the login page (full page load). Printed documents (`app/Views/pdf/`) and the public verify page stay Indonesian. Code, keys and stored data stay English. Tests run with `app.defaultLocale = en` (`phpunit.dist.xml`).
- New UI text: add the key to **both** `en` and `id` files; never hard-code text in views, flash messages or exceptions.

### Models (`app/Models/`)
- Every business model extends **`App\Models\BaseModel`**: array results, timestamps, soft deletes, and automatic `audit_log` rows (only changed columns on update). Lookup models extend **`LookupModel`** (`idForCode('TRANSFER')`).
- Per model: `$allowedFields`, `$validationRules` (labels are derived automatically; override in `$fieldLabels`), `$nullable` (empty form values stored as NULL), `$referencedBy` (blocks deleting rows that documents use: `isInUse($id)`).
- **Always update/delete by primary key** (`update($id, ...)`, `delete($id)`); where-based updates are not audited. Pass `'id' => $id` in update data so `{id}` placeholders in `is_unique` rules work.
- Shield users are not BaseModels; `App\Services\UserService` writes their audit rows manually.

### Services (`app/Services/`)
- `Transaction::run(fn ($db) => ...)`: commit or roll back (and rethrow). Nested calls join the outer transaction.
- `DocumentSequence::next('INV', $date)`: gap-safe numbers; call inside the document's transaction. Formats come from `document_numbering` (Settings → Document numbering, `Settings\Numbering`), defaults in `Config\Documents::$sequences`; `preview()` shows the next number without using it, `validate()` / `format()` are static. Also used for product SKUs (`SKU`, generated in `Products::create`) and BAST numbers.
- `AuditLogger`: manual audit entries / diffs.
- `WithholdingCalculator::calculate($rules, $lines, $customer, $funding, $company)`: pure function returning expected PPN collection / PPh withholding per `tax_withholding_rule` (see `database.md` §8a). Rules come from `TaxWithholdingRuleModel::validOn($issueDate)`.
- `App\Libraries\Uuid::v7()`: time-ordered UUIDs (customer IDs).
- `DocumentTotals::calculate($lines, $shipping, ?CalcSettings)`: line and header totals for proposals, invoices and credit notes (bcmath, rules in `database.md` §11.4: incl.-tax lines from the incl. total, tax per line or per document total, `spread()`). **(rev)** `CalcSettings` (value object, `current()` from company_profile, cached per request, `clearCache()`; `round()` / `roundUnit()`; `toJs()` → `window.AppCalc` in the page head) holds Settings → Calculation (`Settings\Calculation`, `GET|POST settings/calculation`, live examples in `calculation-form.js`). `document-items.js` mirrors it (`App.calculate()`, `App.lineAmounts()`; amounts in BigInt cents, unit prices × 10^6), also used by `credit-note-form.js`. Display: `format_idr()` follows the amount decimals, `format_price()` shows unit prices with up to 6 decimals, `decimal_input()` for number inputs.
- `ProposalRevisions`: negotiation history. `record()` (called by `ProposalService::changeStatus` on PROPOSE, and on STORE_APPROVE when the content changed), `history()` (revisions newest first with `diff()` to the previous one, plus unsent changes), `snapshot()`.
- `OrderFiles::collect()`: all printable PDFs and attachments of an order plus the documents the user may attach files to (part of the `OrderFlow` result as `files`, rendered by `components/order_files`). `AttachmentService`: upload validation (extension + content MIME + size), storage under `writable/uploads/attachments/Y/m/`, access (`canSee()` via AccessScope, `canUpload()` per module permission, `canDelete()` uploader/admin); served by the `Attachments` controller (`POST attachments`, `GET attachments/{id}`, `POST attachments/{id}/delete`).
- `ProductService`: create/update with picture (`App\Libraries\ImageUpload`: content check with `getimagesize()`, random name in `writable/uploads/products/`, streamed by `Products::image()` / `variantImage()`), delete (with variants), `saveVariant()` (SKU `<product SKU>-NN` under a product row lock, name unique per product) and `deleteVariant()` (blocked when used). `ProductModel::lineDefaults()` returns one picker entry per active variant (title "product - variant", variant SKU and price, product description, `image_url`); `DocumentLines` requires a variant when the product has active ones and copies `variant_id` and `item_description`.
- `CustomerService::assignRep()`: assigns the school to the sales rep set on a proposal (create/update) or invoice (update), idempotent; existing documents were backfilled by migration 700003.
- **(rev) Contacts & CRM:** `ContactService` (people shared by schools: `addToCustomer()` existing or new person, `updateLink()`, `savePerson()`, `removeLink()`; one primary among current contacts, used links are ended instead of removed); `CustomerService::saveContact()` / `deleteContact()` delegate to it (quick-add). `ActivityService` (`save()` log or follow-up, optional next follow-up; `complete()` with outcome; `canEdit()`), `ActivityPanel::forCustomer() / forProposal() / forInvoice()` feeds `components/activity_panel` (timeline + log / plan modals; items in `components/activity_item`). Controllers `Contacts` (list, page, edit, `GET api/contacts?q=` person picker), `CustomerContacts` (link on the school page), `Activities` (list with filters open / overdue / today / done / all, mine / everyone; edit, complete, delete; forms post `return_to`). Dashboard "My follow-ups" (assigned to me, due within 7 days or overdue). `AgreementService::defaults()` takes the school's HEADMASTER (with NIP) as client signatory.
- `CustomerService::quickAdd()`: school + optional billing address + primary contact from the proposal form (`POST api/customers/quick`, JSON, returns the new CSRF token).
- `Search` controller: top bar quick search (`GET search?q=`) over proposals, invoices, delivery notes and customers, scoped; htmx requests get `search/results` only.
- `ProposalWorkflow`: proposal status labels, allowed transitions (with required permission, note and "needs items" flags) and which statuses are editable. `ProposalService`: create/update (number, items copied from products, totals) and `changeStatus()` (row lock, permission check, `proposal_status_history`).
- `DocumentLines`: shared item-line handling for proposals and draft invoices (`prepare()` validates posted rows, `sync()` updates/inserts/soft-deletes lines). **(rev)** Per line: `tax_code` (Dolibarr style; default from the product, choices from `App\Services\LineTax::options()` = tax codes valid on the date with rate > 0, none when not PKP), `price_base` EXCL/INCL (INCL prices are converted with `DocumentTotals::exclFromIncl()` and kept in `unit_price_incl`), minimum price check (`prices.override`). `document-items.js` mirrors the conversion (`App.exclFromIncl`), shows the other-base price and a below-minimum warning.
- `InvoiceWorkflow`: invoice status labels, `PAYABLE` statuses and `statusFor()` (payment status derived from the amounts). `InvoiceService`: `createFromProposal()` (DRAFT with placeholder number, items copied, one non-void invoice per proposal), `update()` / `deleteDraft()` (DRAFT only), `issue()` (INV number, issue/due date, expected withholding stored, lock), `void()` (admin, nothing paid/credited), `refreshStatus()`, `markOverdue()`. All with the invoice row locked (`lockInvoice()`).
- `PaymentService::record()`: cash + `payment_withholding` rows, no overpayment, updates `amount_paid` / `withheld_total` and the status; `updateProof()` completes a bukti potong / NTPN later. `CreditNoteService::create()`: credit lines per invoice line (caps in `database.md` §11.7), CN number, `credit_total`, status.
- Scheduled command `php spark invoices:mark-overdue` (`app/Commands/MarkOverdueInvoices.php`), run daily.
- `Reports` (service, built with an `AccessScope`): `receivables($today, $filters)` (open invoices with aging buckets `BUCKETS`, taxes pending = expected − withheld, cash expected; per customer and per invoice) and `withholding($from, $to, $filters)` (invoice_withholding vs. payment_withholding of non-reversed payments; `STATES` ok / missing_proof / difference / not_withheld / unexpected). `Reports` controller renders them and exports CSV (`?export=csv`: semicolon, decimal comma, UTF-8 BOM, formula-safe cells).
- `php spark app:check` (`app/Commands/AppCheck.php`, permanent): production readiness (PHP extensions and limits, environment, HTTPS, encryption key, writable folders, **(rev)** backup folder and latest backup, migrations, protection triggers, seeds, admin user, company data).
- **(rev) Backups:** `BackupService` (`create()`, `list()`, `manifest()`, `path()` (file-name check), `delete()`, `prune()`, `restore()`; settings in `Config\Backup`: path, uploads / session paths, keepDays / keepMin, overridable in `.env`). Pure-PHP dump over the app connection in a consistent snapshot (`App\Libraries\BackupSql`: one statement per line, escaped values, binary as hex) + `writable/uploads/` + `manifest.json` (app migration version, row counts, sha256) in a PharData `.tar.gz`, with a `.json` copy of the manifest next to it. A lock file prevents parallel runs. `restore()`: checks checksum and version, makes a `pre-restore` safety backup, drops and rebuilds all tables (triggers are removed: DBA reinstalls), replaces uploads, deletes sessions, runs newer migrations, writes an audit row. Commands (permanent): `backup:create [--label x] [--prune]` (daily job with `--prune` = scheduled), `backup:list`, `backup:restore <file> [--force]`. Controller `Settings\Backups` (`settings/backups`: list, create, `{file}/download`, `{file}/delete`, `{file}/restore` with the word RESTORE; page script `backups.js`).
- `PaymentService::record(..., $acceptOverpayment)` (overpayment only when confirmed) and `reverse()` (failed/mistaken payment: marked reversed, totals and status recomputed). `RefundService::record()` / `reverse()`: refunds from a credit balance, capped by `InvoiceModel::refundable()` (cash only; withheld taxes are reclaimed by the treasurer, `InvoiceModel::taxToReclaim()`).
- `CreditNoteService::create($invoiceId, ['reason', 'reason_type', 'shipping_amount'], $lines, $userId)`: also for PAID invoices; crediting everything (cancellation) → CANCELLED.
- `DeliveryService`: delivery notes for issued invoices (goods lines, remaining quantities, DO number), `update()` (header while open), `markShipped()`, `addUpdate()` (tracking event), `markDelivered()`, `cancel()`; every step is logged in `delivery_note_event` (`DeliveryEventModel`).
- `OrderFlow::forProposal()` / `forInvoice()`: the order tracker (steps proposal → invoice → payment → delivery with state done/current/pending/cancelled/skipped, plus all linked documents), rendered by `components/order_flow` on the proposal, invoice and delivery note pages. Work-queue filters: proposals `status=to_invoice`, invoices `status=to_ship|refund_due|unpaid|past_due`, deliveries `status=open`; the dashboard "Order pipeline" links to them.
- Tamper protection: `App\Database\Support\ProtectionTriggers` (DB triggers), installed by a DBA from `php spark db:protection-sql` (`--check` shows what is installed).
- New document lines copy their values from `ProductModel::lineDefaults()`: the tax rate is the product's tax code rate valid on the date, and 0 when the company is not PKP. On edit, existing lines keep their copied unit/type/tax; only title, quantity, price and discount change.
- Multi-row business rules live in services (`CustomerService`: UUID, sales reps, one primary contact, one default address per type; `UserService`; `ProposalService`; `InvoiceService`; `PaymentService`; `CreditNoteService`). Services throw `ValidationFailed` (field errors) or `RuntimeException` (business rule message).

### PDF documents
- Libraries: **Dompdf 3** (`App\Libraries\Pdf`: A4, DejaVu Sans, remote loading and PHP off, images as data URIs, page numbers + footer drawn on every page) and **chillerlan/php-qrcode** (verification QR). Both need the PHP `gd` extension in the web server process (restart `php spark serve` / PHP-FPM after enabling it).
- Seller on every document = the company profile (**Warung Sahabat**: name, address, NPWP, logo, signatory, standard invoice notes and SPK clauses in Settings → Company). Group line in the footer: `Config\Documents::$groupName` (de'makmur) + `$groupLogo`. Fallback store logo `public/assets/img/store-logo.png`.
- Documents (views `app/Views/pdf/`, data assembled by `App\Services\PrintDocuments`, served by `Documents` controller; `?download=1` downloads):
  | Document | Route | Number |
  |---|---|---|
  | Surat Penawaran Harga | `GET proposals/{id}/pdf` | QUO |
  | Surat Perintah Kerja (agreement) | `GET proposals/{id}/agreement/pdf` (create/edit: `proposals/{id}/agreement`) | SPK |
  | Invoice | `GET invoices/{id}/pdf` | INV |
  | Kwitansi (per payment: cash + withheld taxes) | `GET payments/{id}/receipt` | KW (assigned when the payment is recorded) |
  | Surat Jalan | `GET deliveries/{id}/pdf` | DO |
  | Berita Acara Serah Terima | `GET deliveries/{id}/handover` | BAST (= DO number with BAST prefix) |
- Printed labels are **Indonesian** and live only in `app/Views/pdf/` (code stays English). Helpers: `format_date_id()`, `date_words_id()` (BAST/SPK "Pada hari ini ..."), `terbilang()`, `format_amount()`. Partials (`_header`, `_parties`, `_items`, `_goods`, `_signatures`) are rendered with `pdf_part()` (no shared view data); each document uses its own renderer instance.
- Watermarks: DRAFT (draft proposal/invoice), BATAL (cancelled/void/reversed), LUNAS (paid invoice). Meterai box when the amount exceeds `Config\Documents::$stampDutyThreshold` (Rp 5.000.000).
- **Scan to verify:** `DocumentVerification` gives every printed document a random token (`document_verification`); the QR opens the public page `GET verify/{token}` (no login, Indonesian) showing number, date, customer, amount and whether the document is still valid.
- Generated on demand, not stored.

### Controllers (`app/Controllers/`)
- Thin; extend `BaseController` helpers: `postFields([...])`, `backWithErrors($errors)`, `findOr404($model, $id)`, `userId()`, `failed($e, 'context')` (logs + generic flash).
- URL pattern per module: `GET x`, `GET x/new`, `POST x`, `GET x/{id}`, `GET x/{id}/edit`, `POST x/{id}`, `POST x/{id}/delete`. Routes in `app/Config/Routes.php` grouped by `permission:<scope>.view` / `<scope>.manage` filters inside the `session` group.
- CSRF is enabled globally (`Config\Filters`); every form includes `csrf_field()`.
- Custom validation rules (`npwp`, `phone`) in `app/Validation/AppRules.php`.

## Frontend Standards
- One staff layout: `layouts/app_layout.php` (sidebar + top bar). Shield pages use `layouts/auth_layout.php`.
- **Single-page navigation with htmx** (2.0.4, vendored in `public/assets/vendor/htmx/`): `<body hx-boost="true">` turns links and forms into AJAX requests that swap `<body>`; the server still renders full pages (no partial endpoints needed). Rules:
  - Global scripts (Bootstrap, htmx, `app.js`, `typeahead.js`, `document-items.js`, `cascade-select.js`) load once in `layouts/common/head.php`. They may only define functions and **delegated** listeners; per-content setup goes in `htmx.onLoad`.
  - Page scripts (`pageScripts` section) run again after every navigation: they work on their own elements only, never add `document` listeners, and are the single init script of the page.
  - Downloads and anything that is not an HTML page: `hx-boost="false"` (or `target="_blank"`). Forms posted by their own `fetch()` code: `hx-boost="false"`.
  - The current CSRF token lives in `<div id="csrf-state">` in the body (head is not swapped); use `App.getCsrf()` / `App.refreshCsrf(token)`.
  - `app.js` handles: progress bar (`html.is-loading`), cleanup of modal backdrops, login page / error responses (full page load), confirm dialogs and upload size check in the capture phase (before htmx submits), toasts (`App.toast()`), live list filters, quick search dropdown.
  - `htmx-config` meta: no history cache (back = fresh page load).
- **Live list filters:** a list's filter form has `data-live-filter` and its results card `id="list-results"`; typing / choosing refreshes only `#list-results` (URL updated with `replaceState`).
- Sidebar menu is defined in `app/Config/Navigation.php`; items are hidden when the user lacks the item's permission.
- Bootstrap 5 utility classes; modular vanilla JS in `public/assets/js/`: `app.js` (confirm dialogs, CSRF), `typeahead.js` (`App.typeahead` search-as-you-type over a JSON endpoint), `document-items.js` (`App.documentItems`: editable item table from `components/item_row_template`, live totals with BigInt decimals, same rounding as `DocumentTotals`, optional shipping input; `App.productPicker`; helpers `toScaled`, `roundDiv`, `formatIdr`), `proposal-form.js`, `invoice-form.js`, `payment-form.js` (live balance, overpayment confirmation), `credit-note-form.js` (live credit totals, "credit everything"), `cascade-select.js` (nested dropdowns via `data-cascade-target` / `data-cascade-url`, e.g. province → regency/city), `delivery-form.js`.
- Display money with `format_idr()` and quantities with `format_qty()` (`app/Helpers/format_helper.php`). Names / titles / addresses with `up()` (stored lower case, see `database.md` §0); their inputs carry `.text-uppercase`. `month_label()` for month names in the screen language.
- Form helpers (`app/Helpers/ui_helper.php`): `form_value()`, `form_checked()` (render a hidden `0` input before each checkbox), `invalid()`, `field_error()`, `active_badge()`, `proposal_status_badge()`, `invoice_status_badge()`, `user_can()`, `format_date()`.
- Components (`app/Views/components/`): `order_files` ("Documents & files": PDFs + attachments + upload), `page_header` (title, breadcrumb, actions), `delete_button` (POST + confirm dialog via `data-confirm`), `stat_card` (optional note and link), `item_row_template`, `region_selects` (province + regency/city cascading selects; `RegionModel` lists), `reason_modal` (POST with a required reason: void, reverse, cancel), `order_flow` (order tracker + linked documents). Pagination: `$pager->links('default', 'bootstrap')`.

## API / Integration
- JSON endpoints only where the UI needs them (`Api\Lookup`: `GET api/products?q=`, `GET api/customers?q=` (scoped), `GET api/customers/{id}` for contacts and reps, `POST api/customers/quick` (quick-add school), `GET api/regions[?parent=code]` for provinces / regencies; `GET settings/numbering/preview` for the numbering form). For POST requests, include the CSRF header from the `<meta name="csrf-token">` tag.
- The app timezone is `Asia/Makassar` (WITA, server location) (`Config\App::$appTimezone`). It decides document dates and monthly number periods.

## Testing
- `composer test` runs PHPUnit 10 (`phpunit.dist.xml`, bootstrap `tests/bootstrap.php` with the PHP 8.6 session workaround).
- `tests/unit/`: pure logic, no database. `tests/feature/`: extend `Tests\Support\AppTestCase` (DatabaseTestTrait): all migrations run on a fresh **`test_md_invoice`** database per test class and the lookups are seeded; helpers `createUser()`, `createCustomer()`, `createProduct()`, `approvedProposal()`, `issuedInvoice()`. In the `testing` environment `Config\Database` uses the default credentials with that database and refuses any database not starting with `test` (the working database is never touched). The app DB user may create `test_*` databases.
- Migrations must roll back cleanly (`down()`), because feature tests regress and re-run them; use `BaseMigration::dropForeignKeyIfExists()` / `indexExists()`.

## Deployment (production)
Full guide: `DEPLOYMENT.md` (requirements, php.ini, database user and grants, migrations and seeds, protection triggers, first admin, Apache/Nginx, scheduled job, backups, updates); settings template `env.production.example`; check with `php spark app:check`.
- **Scheduled job:** one OS scheduler entry runs `php spark invoices:mark-overdue` daily, shortly after midnight WITA (Linux cron: `5 0 * * * cd /path/to/app && php spark invoices:mark-overdue >> writable/logs/cron.log 2>&1`; Windows: Task Scheduler, daily, "Start in" = app folder). The command is idempotent and logs errors. If more jobs are added (reminders, reports), switch to the official `codeigniter4/tasks` package: one cron entry `* * * * * php spark tasks:run` and the schedule in code.
- **Database users:** the app user needs SELECT/INSERT/UPDATE/DELETE (+ DDL only for running migrations), **not** TRIGGER or SUPER. A DBA installs the protection triggers once with `php spark db:protection-sql > protection.sql` and re-runs it after migrations that touch protected tables; check with `php spark db:protection-sql --check`. Never install the `--dev` variant in production.
- Back up the database daily; the audit log and financial records are append-only, so backups are the only way to recover from a lost server.
